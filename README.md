# course-services

Учебный backend на Python. В `course-service` реализованы курсы, задания, решения студентов, ревью и файлы. Остальные сервисы пока являются заглушками.

## Запуск

Нужны Python 3.14, `uv` и Docker.

```bash
cd course-service
uv sync
```

Создать `.env` в папке `course-service`:

```dotenv
DATABASE__DSN="postgresql://postgres:postgres@localhost:5432/courses"
AUTH__SECRET="replace-with-a-long-random-secret"
```

Запустить базу и приложение:

```bash
docker compose up -d postgres
uv run alembic upgrade head
uv run uvicorn src.main:app --host 127.0.0.1 --port 8888 --env-file .env --log-config log-config.yaml
```

Документация API: http://127.0.0.1:8888/docs. Для работы с API нужен JWT HS256 с полями `sub`, `role` и `exp`, подписанный ключом `AUTH__SECRET`.

Для проверки решений добавить в `.env` переменную `CHECKER__URL` с адресом сервиса проверки. Затем в другом терминале из папки `course-service` запустить обработчик:

```bash
uv run python -m src.infrastructure.outbox_worker
```

Без адреса проверки решения и события сохраняются, но проверка не запускается. Обработчик подберёт их после настройки адреса.

## Тесты

Из папки `course-service`:

```bash
uv run pytest
```

Без базы часть тестов пропускается. Для всех тестов запустить PostgreSQL и выполнить:

```bash
TEST_DATABASE_DSN=postgresql://postgres:postgres@localhost:5432/postgres uv run pytest
```

Тесты сами создают и удаляют отдельную базу. Пользователю PostgreSQL нужно право создавать базы.

## ADR: лабораторная №4

### Выбор архитектуры

| Подход | Суть и применимость |
| --- | --- |
| MVC | Разделяет модель, представление и контроллер. Для нашего API представления не нужны. |
| MVP | Presenter управляет интерфейсом. Больше подходит для UI. |
| MVVM | Связывает интерфейс с состоянием ViewModel. Здесь это не требуется. |
| Layered | Разделяет маршруты, сервисы и работу с базой. Уже используется в проекте. |
| Hexagonal | Отделяет бизнес-логику через порты и адаптеры. Позволяет заменять внешние зависимости. |
| Clean | Выделяет бизнес-сценарии, которые зависят от интерфейсов. Выбрали для создания решения студента. |

Используем упрощённую Clean Architecture: правила создания решения находятся в `CreateSubmissionUseCase`, SQL — в репозиториях, транзакцией управляет `UnitOfWork`. Остальные сценарии оставили в существующих сервисах.

Use Case работает через `Protocol`, поэтому в тестах вместо PostgreSQL можно передать FakeUnitOfWork. Проверяются права студента, участие в курсе и лимит в 10 попыток.

### Паттерны

- **Adapter (GoF)** связывает существующие репозитории с интерфейсами Use Case.
- **Repository** хранит SQL-запросы отдельно от бизнес-правил.
- **Unit of Work** объединяет запись решения, события и ответа для ключа идемпотентности в одну транзакцию. При ошибке всё откатывается. `create_once()` использует то же соединение.
- **Transactional Outbox** сохраняет событие проверки вместе с решением. Отдельный обработчик выполняет проверку и отмечает событие выполненным.

Repository, Unit of Work и Outbox не относятся к GoF.

Повтор запроса с тем же ключом не создаёт новое решение. Обработчики используют `FOR UPDATE SKIP LOCKED`, чтобы не брать одно событие одновременно. При ошибке проверки повтор происходит через 5 секунд; после сбоя процесса событие остаётся в базе. `BackgroundTasks` только ускоряет запуск, отдельный обработчик обеспечивает доставку.

При повторной отправке checker получает тот же JSON и `Idempotency-Key`. Он должен поддерживать этот ключ, чтобы не создавать результат повторно. Гарантии exactly-once нет.

### Принципы и ограничения

- **DRY:** повторно используем репозитории, транзакции и проверку решений.
- **KISS, YAGNI:** один Use Case и простой обработчик без брокера сообщений.
- **APO:** не добавляем оптимизации без необходимости.
- **GRASP, SOLID:** разделяем обязанности; бизнес-логика зависит от интерфейсов.
- **BDUF:** заранее определили границы слоёв, не проектируя все будущие сервисы.
- **ООП:** связываем объекты через композицию и используем разные реализации интерфейсов.

Плюсы: правила легко тестировать отдельно, а задача проверки не теряется при остановке API. Ограничения: во время HTTP-проверки занято соединение с базой, готовые события пока не очищаются. Промежуточные статусы видны только внутри транзакции. Для простоты Use Case использует существующие Pydantic-схемы из `web/schemas`.
