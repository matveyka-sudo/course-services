# course-services

Учебный проект по Python backend. Тут задумано четыре сервиса: `course-service`, `bff`, `code-coordinator` и `plagiarism-service`. Пока реализован `course-service`, в остальных папках лежат заглушки.

## Как запустить

Нужны Python 3.14, `uv` и PostgreSQL 17. Из корня репозитория:

```bash
cd course-service
uv sync
```

В этой папке создать `.env`:

```dotenv
APP__TITLE="Course Service"
APP__DESCRIPTION="Course service API"
APP__SUMMARY="Course service"
APP__VERSION="0.1.0"
DATABASE__DSN="postgresql://postgres:postgres@localhost:5432/courses"
AUTH__SECRET="replace-with-a-long-random-secret"
# Адрес существующего HTTP-сервиса проверки решений:
# CHECKER__URL="http://localhost:9000/check"
```

Запустить базу, применить миграции и запустить API:

```bash
docker compose up -d postgres
uv run alembic upgrade head
uv run uvicorn src.main:app --host 127.0.0.1 --port 8888 --env-file .env --log-config log-config.yaml
```

После запуска доступны `http://127.0.0.1:8888/service` и `http://127.0.0.1:8888/docs`. Для защищённых маршрутов нужен JWT HS256 с `sub` (строковый ID пользователя), `role` и `exp`, подписанный значением `AUTH__SECRET`.

Для проверки решений задать настоящий `CHECKER__URL` в `.env` и в отдельном терминале из `course-service` запустить:

```bash
uv run python -m src.infrastructure.outbox_worker
```

Обработчик сам читает тот же `.env`. Без `CHECKER__URL` он завершится с пояснением. API без этого адреса продолжает принимать решения и сохранять события, но не запускает проверку. После настройки адреса обработчик подберёт накопленные события. Запрос в checker и ожидаемый ответ не менялись: JSON решения и ответ `{"status": "COMPLETED"}`.

## Тесты

Из папки `course-service`:

```bash
uv run pytest
```

Без `TEST_DATABASE_DSN` запускаются изолированные тесты и тесты приложения без базы; интеграционные тесты пропускаются. Для всех тестов нужен PostgreSQL и пользователь с правом создания баз:

```bash
TEST_DATABASE_DSN=postgresql://postgres:postgres@localhost:5432/postgres uv run pytest
uv run ruff check src/application src/infrastructure src/web/services tests/test_create_submission.py tests/test_outbox.py migrations/versions/0002_outbox.py
uv run mypy src
```

Интеграционные тесты создают отдельную временную базу, применяют миграции и удаляют её после проверки. Проверяем бизнес-правила через FakeUnitOfWork, HTTP API, конкурентные попытки, идемпотентность, откат записи в Outbox, доставку, задержку повтора, несколько обработчиков и восстановление после сбоя или отмены.

## ADR: архитектура приложения, лабораторная №4

**Решение принято:** для создания решения студента используем упрощённую Clean Architecture со слоями. До рефакторинга весь сценарий находился в `SubmissionService`. Теперь бизнес-правила собраны в `CreateSubmissionUseCase`, SQL остаётся в репозиториях, а граница транзакции выражена через Unit of Work. Остальные сценарии сохраняют существующую слоистую организацию.

### Какие варианты сравнили

| Подход | Основная идея | Применимость к сервису |
| --- | --- | --- |
| MVC | Модель, представление и контроллер разделены | Подходит для веб-приложений с представлениями, но не определяет наши транзакции и границы бизнес-логики |
| MVP | Presenter управляет пассивным View | Полезен для UI, в нашем HTTP API отдельного View нет |
| MVVM | View связан с состоянием ViewModel | Подходит для интерфейсов с привязкой данных, здесь такой задачи нет |
| Layered | Маршрут, сервис и доступ к данным разделены на слои | Уже применяется, но сервисы напрямую зависят от SQL-репозиториев |
| Hexagonal | Бизнес-логика общается с внешним миром через порты и адаптеры | Даёт заменяемый доступ к данным; используем эту идею в портах репозиториев |
| Clean | Сценарии приложения зависят от абстракций, инфраструктура реализует их | Выбрали для создания решения, чтобы тестировать правила без PostgreSQL |

Clean и Hexagonal близки по направлению зависимостей. Clean выделяет use case как отдельный сценарий. Для этой лабораторной достаточно одного такого сценария, без переноса всех сервисов и введения отдельной модели для каждой сущности.

### Как устроен сценарий

```text
Router -> SubmissionService -> CreateSubmissionUseCase
                |                       |
          UnitOfWork              UnitOfWorkPort
                |
       адаптеры репозиториев -> PostgreSQL
                |
          событие Outbox -> OutboxWorker -> CheckerService -> HTTP checker
```

`Protocol` описывает необходимые операции, а не дополнительный этап выполнения. Use Case получает `UnitOfWorkPort` и не импортирует `asyncpg`, `Database` или конкретные репозитории. В тестах передаём FakeUnitOfWork. Реальный UoW находится в `infrastructure` и создаёт адаптеры с одним соединением.

Сохранили проверки роли, существования задания и курса, участия студента и лимита в 10 попыток. Задание блокируется перед подсчётом попыток, как и раньше, поэтому параллельные запросы не получают одинаковый номер попытки.

`SubmissionService` открывает UoW и передаёт его соединение в `BaseService.create_once()`. Этот метод по-прежнему блокирует ключ идемпотентности, сравнивает отпечаток запроса и сохраняет исходный ответ. Если соединение передано, новую транзакцию он не открывает. Для остальных сервисов вызов без соединения работает как раньше. Проверка роли до `create_once()` нужна и для повторного запроса, когда сам Use Case уже не выполняется.

Решение, событие и ответ для ключа идемпотентности записываются в одной транзакции. UoW использует существующий `Database.transaction()`: успешный выход подтверждает всё, исключение откатывает всё. Use Case выполняется внутри уже открытого UoW. Нельзя отдельно запустить его без этой границы и ожидать атомарной записи.

### Зачем нужен Outbox

Обычная задача `BackgroundTasks` может потеряться при остановке процесса. Теперь после создания решения в `outbox_events` сохраняется событие с исходным JSON. Один `submission_id` соответствует одному событию. Повтор запроса с тем же ключом возвращает сохранённый ответ и не создаёт ещё одно решение или событие.

Отдельный обработчик выбирает готовое событие через `FOR UPDATE SKIP LOCKED`. Пока он проверяет решение, блокировка события удерживается. Другой обработчик может взять другое событие. `CheckerService` использует это же соединение: даже пула из одного соединения достаточно. Успешный статус решения и отметка выполнения события подтверждаются вместе. В этом пути промежуточные `PENDING` и `PROCESSING` остаются внутри транзакции; через API виден последний подтверждённый статус.

При ошибке HTTP, таймауте или неверном ответе сохраняются `FAILED` и время следующей попытки через 5 секунд. Ошибки базы откатывают транзакцию; цикл обработчика пишет ошибку в журнал и повторяет чтение. После остановки или отмены процесса незавершённая транзакция откатывается, блокировка снимается, событие остаётся доступным. Уже завершённое решение повторно в checker не отправляется.

Для быстрого запуска сохранили `BackgroundTasks`, но теперь задача вызывает обработку конкретного события Outbox. Надёжность обеспечивает запись в базе и отдельно запущенный обработчик. Обе точки запуска используют одну реализацию и одну блокировку.

Доставка допускает повтор: checker мог выполнить запрос, а наш процесс остановиться до коммита. Поэтому при повторе отправляются тот же `Idempotency-Key = submission.id` и точно тот же JSON из Outbox. Внешний checker должен сохранять результат по этому ключу и возвращать его без повторного создания результата. Без поддержки идемпотентности на принимающей стороне гарантировать отсутствие повторного внешнего эффекта нельзя. Exactly-once не заявляем. Сам сервис новых записей ревью при автоматической проверке не создаёт: существующий checker меняет статус решения.

### Паттерны и принципы

Из GoF применили **Adapter**: `SubmissionAdapter`, `AssignmentAdapter` и `CourseAdapter` связывают порты с существующими методами, принимающими соединение. Repository отделяет SQL, Unit of Work задаёт общую транзакцию, Transactional Outbox связывает сохранение решения с будущей проверкой. Последние три паттерна не относятся к каталогу GoF. Дополнительные GoF-паттерны для этого сценария не потребовались.

- **DRY:** используем прежние репозитории, `Database.transaction()`, `create_once()` и алгоритм checker; обе точки доставки используют `OutboxWorker`.
- **KISS и YAGNI:** один сценарий, одна таблица событий, простой цикл без брокера и универсальной системы событий.
- **APO:** сначала обеспечиваем корректность; частичный индекс помогает выбирать необработанные события, дополнительное кеширование не вводим.
- **GRASP:** правила принадлежат Use Case, SQL — репозиториям, транзакция — UoW. Ответственности разделены, связность уменьшена.
- **SOLID:** классы решают отдельные задачи, порты содержат нужные операции, инфраструктуру можно заменить совместимыми объектами. Бизнес-логика зависит от контрактов; подстановку проверяем тестами.
- **BDUF:** заранее определили границы и транзакцию, но не проектируем все будущие сервисы целиком.
- **ООП:** объекты объединяют состояние и операции, композиция связывает UoW и репозитории, Protocol позволяет использовать разные реализации.

### Последствия и ограничения

Правила создания решения тестируются без базы. Сохранение события атомарно, а остановка приложения не теряет задание на проверку. HTTP-эндпоинты, схемы и остальные сервисы сохранены.

Это упрощённая архитектура: Pydantic-модели пока остаются в `web/schemas` и используются в Use Case как DTO. Не вводим их копии только ради структуры каталогов. На время HTTP-вызова удерживается транзакция и соединение, поэтому нужны короткий таймаут checker и разумное количество обработчиков. Для учебного сервиса это понятный компромисс; при росте нагрузки можно перейти к выдаче событий с арендой. Выполненные события пока не очищаются автоматически. Outbox-обработчик нужно запускать отдельно и следить за его журналом.
