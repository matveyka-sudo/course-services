# Course Service

API учебных курсов на FastAPI, PostgreSQL и asyncpg. Миграции выполняются через Alembic. Нужны Python 3.14, uv и PostgreSQL 17.

## Запуск

Из каталога `course-service`:

```bash
uv sync --group dev
docker compose up -d --wait postgres
```

Добавь в существующий `.env` настройки из `.env.example`. Если `.env` ещё нет, можно скопировать пример. Укажи `DATABASE__DSN` и замени `AUTH__SECRET` на случайную строку длиной не менее 32 символов. Создать её можно командой `uv run python -c 'import secrets; print(secrets.token_urlsafe(48))'`.

```bash
uv run alembic upgrade head
uv run uvicorn src.main:app --host 127.0.0.1 --port 8888 --no-access-log
```

Если PostgreSQL установлен отдельно, создание БД выполняется до миграций, Docker не требуется. Приложение открывает пул соединений при запуске и закрывает при остановке. Миграции автоматически не запускаются.

Swagger: http://127.0.0.1:8888/docs. Состояние приложения: `/service`. Спецификация: `/openapi.json`.

Роутеры валидируют входные данные и вызывают сервис. Сервис проверяет права, выполняет бизнес-операцию внутри транзакции и возвращает Pydantic-модель. Все SQL-запросы приложения находятся в репозиториях; методы репозиториев — `@classmethod`.

Общие настройки схем находятся в `BaseSchemaModel`, общие поля `id`, `created_at`, `updated_at` — в `EntitySchema`. Для PATCH поля можно пропускать, но нельзя передавать `null` или менять связи между сущностями. Общие ограничения строк и идентификаторов вынесены в базовый модуль схем.

Поля тел запросов в исходном контракте были свободными объектами. Они уточнены явными моделями; адреса, операции, ограничения доступа, коды бизнес-ошибок и пагинация сохранены. Версия OpenAPI обновлена до 3.1.0 для схем Pydantic 2. Swagger получает схемы из кода, а описания операций, роли и ошибки — из `openapi.yaml`.

## Авторизация и данные

Внешний сервис выдаёт JWT с подписью HS256 и обязательными полями:

```json
{"sub": "10", "role": "student", "exp": 1893456000}
```

`sub` — строка с целочисленным идентификатором пользователя; роли: `admin`, `professor`, `student`. Сервис проверяет подпись, срок действия и роль. Для проверки издателя и получателя доступны `AUTH__ISSUER` и `AUTH__AUDIENCE`. Отдельного API выпуска токенов здесь нет.

Пользователи существуют во внешней системе, локальной таблицы пользователей нет. Администратор указывает преподавателя и начальный состав студентов при создании курса:

```json
{
  "title": "Backend на Python",
  "description": "Асинхронное программирование",
  "professor_id": 1,
  "student_ids": [10, 11],
  "status": "PUBLISHED"
}
```

Для создания задания нужны `course_id`, `title` и необязательное `description`. Для решения — `assignment_id` и `solution`; автор берётся из JWT. Для ревью — `grade` от 0 до 100 и необязательный `comment`. Файлы загружает преподаватель через multipart-поле `file`; содержимое хранится в PostgreSQL, API возвращает метаданные. Размер ограничивается `MAX_UPLOAD_BYTES`.

Все POST требуют `Idempotency-Key`. Ключ хранится в БД вместе с отпечатком запроса и исходным ответом, в одной транзакции с ресурсом. Повтор возвращает исходный ответ, включая первоначальный статус решения `SUBMITTED`. Изменение тела с прежним ключом даёт 409. Ключ ограничен пользователем и операцией; путь к решению входит в отпечаток ревью и файла.

Advisory lock PostgreSQL сериализует запросы с одинаковым ключом. При отправке решения блокируется строка задания: подсчёт попыток и вставка выполняются атомарно. Ограничение в 10 попыток учитывает все статусы, в том числе `FAILED`. Эти блокировки работают между несколькими экземплярами приложения. Пагинация и её `total` читаются в одной транзакции с уровнем `REPEATABLE READ`.

## Middleware на примере

`RequestMiddleware` подключается один раз в `create_app`. Это ASGI-middleware: вместо `call_next` оно вызывает следующее приложение через `await self.app(scope, receive, send_response)`.

Например, студент отправляет `POST /api/v1/submissions`:

1. Middleware принимает корректный UUID из `X-Request-ID` или создаёт новый. Сохраняет его в состоянии запроса и в `ContextVar`, запускает таймер.
2. Передаёт управление FastAPI. Зависимости проверяют JWT и ключ идемпотентности, Pydantic проверяет тело, сервис создаёт попытку через репозиторий.
3. Обёртка `send_response` перехватывает начало ответа и добавляет `X-Request-ID`. Клиент получает 201 и решение в статусе `SUBMITTED`.
4. Middleware записывает метод, путь, HTTP-статус и время до отправки тела ответа. Фильтр из `core/logging.py` добавляет тот же ID в запись лога.
5. В `finally` значение `ContextVar` восстанавливается. Параллельные запросы не смешивают свои ID.

Если данные неверны или доступа нет, обработчики исключений возвращают `application/problem+json` с полями `error.code`, `message`, `status`, `path`, `request_id`. Для 401 добавляется `WWW-Authenticate: Bearer`. Непредвиденная ошибка логируется с traceback, клиент получает обезличенный ответ 500. Токены, тела решений и файлы не логируются.

При указании `CORS_ORIGINS` подключается готовый `CORSMiddleware`. Например: `CORS_ORIGINS=["http://localhost:3000"]`. Браузерному клиенту разрешено читать `X-Request-ID`.

## Внешняя проверка

Чтобы включить проверку, задай полный URL обработчика, например `CHECKER__URL=http://127.0.0.1:9000/check`. Без URL решения остаются в `SUBMITTED`, доступна ручная проверка преподавателем.

После отправки HTTP-ответа фоновая задача меняет статус на `PENDING`, получает разрешение семафора, ставит `PROCESSING` и отправляет JSON решения внешнему сервису. В запрос передаются `Idempotency-Key` с UUID решения и `X-Request-ID`. Ожидаемый успешный ответ:

```json
{"status": "COMPLETED"}
```

Сетевые ошибки, неуспешный HTTP-статус, неправильный ответ или таймаут переводят попытку в `FAILED`. Финальная оценка выставляется преподавателем через ревью и не зависит от статуса автоматической проверки.

`CHECKER__CONCURRENCY` ограничивает число одновременных проверок на процесс. `CHECKER__TIMEOUT` ограничивает ожидание семафора и обработку запроса; у HTTP-клиента также настроен таймаут. Во время сетевого вызова соединение с БД не удерживается.

Адрес настоящего проверяющего сервиса пока не задан. Клиент проверен с имитацией HTTP-ответов и сетевым вызовом локального проверяющего HTTP-сервера из приложения, запущенного через Uvicorn. Фоновые задачи выполняются в процессе приложения и не являются устойчивой очередью: при аварийной остановке процесса проверку потребуется запустить повторно отдельным механизмом.

## Миграции

```bash
uv run alembic current
uv run alembic upgrade head
uv run alembic revision -m "change course fields"
```

Миграции описываются явно через операции Alembic; ORM-моделей и autogenerate нет. Первичная миграция создаёт таблицы, внешние ключи, ограничения и индексы. Её upgrade, downgrade и повторный upgrade проверяются тестами в отдельной временной БД.

## Тесты

Для полного набора нужен доступ к PostgreSQL с правом создания временной базы:

```bash
TEST_DATABASE_DSN=postgresql://postgres:postgres@127.0.0.1:5432/postgres uv run pytest --cov=src
```

Тесты создают отдельную БД со случайным именем, применяют миграции, а после проверки удаляют её. Рабочая БД не очищается. Если `TEST_DATABASE_DSN` не указан, интеграционные тесты явно пропускаются; проверки middleware и публичных адресов выполняются без БД.

Проверяются все адреса, права ролей, ошибки, формат ответов по OpenAPI, фиксированные страницы, повторные POST, конкурентные отправки, откат операции при ошибке сохранения ключа, два экземпляра приложения, загрузка файлов, таймауты и ограничение конкурентности внешних вызовов.

Эксперимент с задержками находится в `tests/test_checker.py`: четыре проверки запускаются параллельно с разными значениями семафора и задержками имитируемого сервиса. Запуск с выводом измерений:

```bash
TEST_DATABASE_DSN=postgresql://postgres:postgres@127.0.0.1:5432/postgres uv run pytest tests/test_checker.py::test_checker_concurrency -s -q
```

На локальной проверке четырёх HTTP-вызовов с имитируемой задержкой 30 мс получились следующие результаты. Время включает обновление статусов в PostgreSQL и зависит от машины.

| Конкурентность | Время четырёх проверок | Пиковое число HTTP-вызовов |
| --- | --- | --- |
| 1 | 134 мс | 1 |
| 2 | 69 мс | 2 |
| 4 | 37 мс | 4 |
